Here is a typical Dockerfile for a Node.js app:

```dockerfile
# Use a slim Node.js base image
FROM node:20-alpine

# Set the working directory inside the container
WORKDIR /usr/src/app

# Copy dependency manifests first to take advantage of layer caching
COPY package*.json ./

# Install only production dependencies
RUN npm ci --omit=dev

# Copy the rest of the application code
COPY . .

# Document the port the app listens on
EXPOSE 3000

# Run as the unprivileged user that ships with the image
USER node

# Start the app
CMD ["node", "server.js"]
```

## What each line does

**`FROM node:20-alpine`** picks the starting image. It contains Node.js 20 on Alpine Linux, which is much smaller than the default Debian-based image. Smaller images download faster and expose less attack surface.

**`WORKDIR /usr/src/app`** sets the directory where later commands run. Docker creates it if it doesn't exist, so you don't have to chain `cd` commands.

**`COPY package*.json ./`** copies only `package.json` and `package-lock.json`. This is deliberate. Docker caches each instruction as a layer, and if the files for a step haven't changed, it reuses the cached layer. Because dependencies change far less often than source code, copying the manifests first means `npm ci` only reruns when they change.

**`RUN npm ci --omit=dev`** installs dependencies exactly as pinned in the lockfile. It is stricter and more reproducible than `npm install`. The `--omit=dev` flag skips dev dependencies such as test runners, which keeps the image lean.

**`COPY . .`** brings in the rest of your source code. Pair this with a `.dockerignore` file that lists `node_modules`, `.git`, and `.env`, so you don't copy local clutter or secrets into the image.

**`EXPOSE 3000`** documents that the app listens on port 3000. It doesn't publish the port by itself. You still need `-p 3000:3000` when you run the container.

**`USER node`** switches from root to the built-in `node` user. If someone exploits your app, they get fewer privileges inside the container.

**`CMD ["node", "server.js"]`** sets the default command. The JSON array form runs Node directly as the main process, so it receives signals like SIGTERM and can shut down cleanly.

## Building and running

```bash
docker build -t my-node-app .
docker run -p 3000:3000 my-node-app
```

If your project needs a build step, such as TypeScript or a frontend bundle, use a multi-stage build. Compile in one stage, then copy only the output into a clean final image.

Base 2 (binary) and base 16 (hexadecimal) are directly linked because 16 equals 2^4. That means every hexadecimal digit corresponds to exactly four binary digits (bits). To convert binary to hex, split the bits into groups of four starting from the right, then replace each group with its hex digit. For example, 1101 0110 becomes D6. Going from hex to binary reverses the process: A is 1010, F is 1111. This is why programmers use hex as a compact, readable shorthand for long binary values.

Sun-like stars generally rotate about axes closely aligned with the orbital planes of their planets, and the Sun's spin axis is tilted by only about 6 degrees relative to the ecliptic. Yet a growing number of exoplanet systems, particularly those hosting hot Jupiters around stars of various ages, show large spin-orbit misalignments. The origin of this obliquity remains debated. Existing explanations include planet migration, magnetic interactions with the protoplanetary disk, and internal gravity waves, but none fully explains the observed distribution. Here we propose that stellar winds can tilt the spin axis of a Sun-like star. We model a star with a magnetized wind whose mass and angular-momentum loss is not perfectly symmetric about its rotation axis, for instance because of an inclined magnetic dipole, and compute the resulting torque on the stellar spin. We show that over the main-sequence lifetime the torque can produce a measurable drift in the spin-axis orientation, with a magnitude that depends on the wind strength, the magnetic geometry and the star's moment of inertia. Our results suggest that wind-driven tilting is a plausible but modest contributor to stellar obliquity, and identify the regimes where it could matter. We discuss observational tests, including statistical studies of spin-orbit angles in systems of differing ages and magnetic activity levels, that could confirm or rule out this mechanism.
