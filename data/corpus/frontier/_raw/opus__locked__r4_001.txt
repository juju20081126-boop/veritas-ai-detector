Light doesn't fundamentally travel in straight lines; that's an approximation that works extremely well in everyday situations. In quantum terms, light behaves as a wave (or, for a single photon, a probability amplitude) that spreads out and effectively explores every possible path. When the wavelength is tiny compared with the openings and obstacles it meets, contributions from paths far from the straight line cancel through destructive interference, leaving only the straight-line route with significant amplitude. That's why a flashlight beam looks straight.

A double slit breaks that approximation. The slits are narrow, close in scale to the wavelength, so the wave diffracts through both openings, and the two contributions overlap and interfere on the screen. Each photon still lands at one spot, but the probability pattern reflects both paths.

Here's a clean, production-ready Dockerfile for a typical Node.js app:

```dockerfile
# 1. Start from an official, lightweight Node.js base image
FROM node:20-alpine

# 2. Set the working directory inside the container
WORKDIR /usr/src/app

# 3. Copy only the dependency manifests first
COPY package*.json ./

# 4. Install production dependencies
RUN npm ci --omit=dev

# 5. Copy the rest of the application source code
COPY . .

# 6. Tell Node (and many libraries) to run in production mode
ENV NODE_ENV=production

# 7. Document the port the app listens on
EXPOSE 3000

# 8. Run as the unprivileged "node" user instead of root
USER node

# 9. Define the command that starts the app
CMD ["node", "server.js"]
```

## What each part does

**`FROM node:20-alpine`**
Every Docker image builds on top of another image. This one uses the official Node.js 20 image based on Alpine Linux, which is very small (tens of megabytes instead of hundreds). Node and npm come preinstalled.

**`WORKDIR /usr/src/app`**
Creates the directory if it doesn't exist and makes it the current directory for all following instructions. It keeps your app files organized and avoids writing into the container's root.

**`COPY package*.json ./`**
Copies `package.json` and `package-lock.json` into the image *before* the rest of your code. This matters because of **layer caching**: Docker caches each step, and if these files haven't changed, it can skip reinstalling dependencies on the next build. That makes rebuilds much faster when you've only edited source files.

**`RUN npm ci --omit=dev`**
Installs dependencies exactly as pinned in `package-lock.json`. `npm ci` is faster and more reproducible than `npm install`, and `--omit=dev` skips devDependencies like test frameworks and linters that you don't need at runtime.

**`COPY . .`**
Copies the rest of your project into the working directory.

**`ENV NODE_ENV=production`**
Sets an environment variable. Frameworks such as Express use it to enable optimizations like view caching and less verbose error messages.

**`EXPOSE 3000`**
Documents that the app listens on port 3000. It doesn't actually publish the port; you still do that with `-p` when running the container.

**`USER node`**
The official Node images include a non-root user called `node`. Running as that user limits the damage if your app is ever compromised.

**`CMD ["node", "server.js"]`**
The default command that runs when the container starts. Replace `server.js` with your entry file. Calling `node` directly (rather than `npm start`) lets your app receive shutdown signals like `SIGTERM` properly.

## Add a `.dockerignore`

Create a `.dockerignore` file next to the Dockerfile so `COPY . .` doesn't pull in things you don't want:

```
node_modules
npm-debug.log
.git
.env
Dockerfile
.dockerignore
```

Excluding `node_modules` is especially important: your local modules may be built for a different OS, and the image installs its own anyway.

## Build and run it

```bash
docker build -t my-node-app .
docker run -p 3000:3000 my-node-app
```

The first command builds an image tagged `my-node-app`. The second starts a container and maps port 3000 on your machine to port 3000 inside the container, so you can visit `http://localhost:3000`.

If your app has a build step (TypeScript, a bundler, etc.), you'd typically switch to a multi-stage build: install all dependencies and compile in a first stage, then copy only the compiled output and production dependencies into a slim final image.
